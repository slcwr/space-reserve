# マイグレーション

Flyway がアプリ起動時にこのディレクトリを読み、未適用のものを順に適用する。
適用済みの記録は DB 側の `flyway_schema_history` テーブルに残る。

## 命名

```
V<バージョン>__<説明>.sql
```

区切りはアンダースコア2つ。バージョンは連番（`V1`, `V2`, ...）または
日時（`V20260812_1030`）。チームで並行して作業するなら日時の方が衝突しにくい。

```
V1__create_space_and_reservation.sql
V2__add_reservation_cancelled_at.sql
```

## 守ること

**適用済みのファイルは編集しない。** Flyway はファイルのチェックサムを履歴に記録しており、
既に適用したファイルの中身が変わると検証エラーで起動しなくなる。誤りに気づいたら
新しいバージョンを追加して打ち消す。

**エンティティを追加・変更したら、同じコミットでマイグレーションも書く。**
`spring.jpa.hibernate.ddl-auto` は `validate` なので、両者がずれるとアプリが起動しない。
これは事故を早期に検出するための設定であり、`update` に緩めて回避しない。

**ロールバック用のスクリプトは用意しない。** Flyway Community 版に `undo` は無い。
前進あるのみの運用にする。

## 確認

テストは Testcontainers が起動する使い捨ての MySQL に対してマイグレーションを
最初から流すため、`./gradlew test` が通れば全マイグレーションが空の DB に
適用できることの確認になる。
