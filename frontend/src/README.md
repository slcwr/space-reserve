# src の構成

`src/` を開いた人が最初に読み取るべきなのは「React アプリである」ことではなく
**「スペース予約システムである」こと**。そのため技術名のディレクトリ（`components/`,
`pages/`, `hooks/`, `store/`）を最上位に置かず、ドメインをそのまま並べる。

```
src/
├── authentication/   ログイン・ログアウト・現在ユーザー
├── reservations/     予約
├── spaces/           スペース
├── users/            利用者
├── shared/           どのドメインにも属さない横断的な部品
└── app/              起動と配線（ルータ、プロバイダ）
```

サーバ側は「レイヤ優先」で切ってあり（`backend/` とリポジトリ直下の README）、ここは「ドメイン優先」で
切る。向きが違うのは意図的で、サーバは1つの HTTP 境界を層で守る作りなのに対し、
画面は機能単位で足し引きされるため。**片方に合わせようとしないこと。**

## ドメインの中身

各ドメインは同じ形を持つ。無ければ作らなくてよい。

| | 責務 | 置かないもの |
|---|---|---|
| `api/` | サーバとのやり取りと、その入出力の型 | React の import |
| `model/` | その領域の型と、データだけで決まる判断 | React の import、HTTP の都合 |
| `hooks/` | 画面から使う入口。TanStack Query のラッパ | JSX |
| `components/` | その領域に固有の UI | 他ドメインの import |
| `routes/` | 画面（ページ）と、`app/router.tsx` へ渡すルート定義 | |
| `index.ts` | 公開面 | |

## 依存の向き

```
app  →  各ドメイン  →  shared
```

- **ドメイン同士は原則として依存しない。** どうしても必要なら相手の `index.ts` 経由に限る。
  `@/reservations/api/reservationApi` のような深い import はしない。公開面が定まらないと、
  ドメインを切り出すときに何が壊れるか分からなくなる。
- **`shared/` から各ドメインを import しない。** 向きが逆流する。共通に見えたものが実は
  片方のドメインのものだった、という形で気づく。
- **`app/` だけが全部を知ってよい。** ルータとプロバイダはそういう場所。

`@/` は `src/` を指す（`vite.config.ts` と `tsconfig.app.json` の両方に定義がある）。
ドメインを跨ぐ import が `../../` に埋もれず、import 文を見れば境界を越えたことが分かる。

## 状態

クライアント状態のライブラリは入れない。サーバから取ってきたデータは TanStack Query の
キャッシュが持ち、画面固有の状態は `useState` で足りる。**この2つで収まらない状態が出てきた
ときに初めて検討する。** ログイン状態も専用のストアではなく `useCurrentUser()` の
クエリキャッシュ1つで表している（`authentication/README.md`）。
