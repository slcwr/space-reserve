# authentication/

ログイン・ログアウトと、現在ログインしている利用者の保持。

サーバ側の設計は `docs/design/authentication.md`。ここはその 12 節「フロント側の約束」を
実装したもの。

## ログイン状態の持ち方

**専用のストアを作らず、`useCurrentUser()` のクエリキャッシュ1つで表す。**
状態が2箇所にあると必ずずれる。値は3通り。

| `data` | 意味 |
|---|---|
| `undefined`（`isPending`） | まだ分からない（`/auth/me` 確認中） |
| `null` | 未ログイン |
| `User` | ログイン中 |

`staleTime` を無限にしてあるのは、状態が変わる契機がログイン・ログアウト・セッション切れの
3つしか無く、いずれもキャッシュを明示的に書き換えるため。

## 起動時に `/auth/me` を1回叩く理由

ログイン状態の復元だけが目的ではない。開発時は `GET /` を Vite が返して Spring を通らず、
`XSRF-TOKEN` Cookie が撒かれない。この口を1回通しておかないと**最初のログイン POST が
403 になる**（authentication.md 12 節）。原因が CSRF だと気づきにくい壊れ方をする。

## 401 の2つの意味

- **`/auth/login` と `/auth/me` の 401** — 「資格情報が違う」「まだ誰でもない」という業務上の
  正常な応答。ログイン画面へ飛ばしてはいけないので `skipSessionExpiredHandler` を立てる。
- **それ以外の API の 401** — セッション切れ。`shared/api` のインターセプタが拾う。

## 表示文言

**サーバの `detail` を画面に出さない。** あれは開発者向けの説明という位置づけで、文言は
`model/loginError.ts` がステータスから決める。i18n と文言調整をサーバのデプロイから
切り離すため（authentication.md 12 節）。

「メールアドレスとパスワードのどちらが違うか」は返さない。返すとアドレスの存在を確かめる
手段になる。429 で残り時間を出さないのも同じ理由。
